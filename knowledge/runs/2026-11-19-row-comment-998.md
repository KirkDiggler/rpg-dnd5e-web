# Run — 2026-11-19 — a moved row keeps its comment

Bug [rpg-project#998](https://github.com/KirkDiggler/rpg-project/issues/998), found in the review of [#1451](https://github.com/KirkDiggler/rpg-dnd5e-web/pull/1451#pullrequestreview-5963017053). Base: `rpg-dnd5e-web` `dev` at [`a872ef8e`](https://github.com/KirkDiggler/rpg-dnd5e-web/commit/a872ef8e). Branch `row-comment-998`.

## Cause

Both list editors (the Bundles page's rows, the machine editor's List pop-up) commit a move as the whole list re-ordered; the file is written by `spliceYaml` (`src/concepts/world-building/yamlSplice.ts`). Two things lost the row:

- **Alignment.** Rows without ids align by the longest common subsequence, then the items left between two matches pair in order. A swap of two rows keeps only one in common order; the other was read as removed plus added, and in a longer list it could even be paired, in order, with a different row and "edited" into it.
- **Re-insertion.** `walkSeq` removed a moved item with its comment lines, then inserted `block([value])` — fresh YAML from the value, with no comment and the encoder's own layout (flow `{…}` became block, quoting changed).

## Fix (one helper, both callers)

- `alignItems` pairs a row outside the common order with an equal row on the other side as a **move**, before the in-order pairing of what is left.
- `walkSeq` handles each block item as its **span** of source text (`itemSpan`) and re-inserts a moved item as that text, byte for byte. A moved item that also changed (rows with ids) has its change spliced into its own text (`movedItemEdited`), so its comment and the layout of what did not change stay; it falls back to fresh YAML under its own comment lines when the text does not stand alone.

## The attachment rule

A row's span is:

- the comment lines directly above its dash at the dash's column — a blank line or any other line ends the run;
- the row's own lines, with a comment on its last line;
- comment lines directly below it indented deeper than the dash (they close it).

So a comment written above the list's key, or set off from the first row by a blank line, is the list's and never moves. A comment directly under the key, at the dash column, is the first row's: the castle writes the first `time` row's hand edit there. Blank lines are not part of any row; they keep their place.

## What each operation now preserves

- **Move:** the row's comment, its text byte for byte; every other line unchanged; moving back writes the original file.
- **Remove:** the row's own span goes; its neighbours keep theirs.
- **Add:** the new row is written fresh, after its neighbour's span or above the first steady row's comment; no neighbour's comment moves.
- **Edit in place:** unchanged as before — the comment stays and only the changed scalar is rewritten.
- **Not preserved:** without ids, a row that moves AND changes in one write is read as one removed and one added (no editor does both in one commit). Its comment would go with the removal.
