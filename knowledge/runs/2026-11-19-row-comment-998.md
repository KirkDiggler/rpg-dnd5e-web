Base: `rpg-dnd5e-web` `dev` at [`a872ef8e`](https://github.com/KirkDiggler/rpg-dnd5e-web/commit/a872ef8e). Branch `row-comment-998`, PR [#1459](https://github.com/KirkDiggler/rpg-dnd5e-web/pull/1459).

## Shipped

- **A moved row keeps its comment and its own text.** When a row is moved in one of the studio's lists, the comment lines that belong to it go with it, and the row is written back byte for byte: flow style, quoting and a trailing comment on its line are all kept. Every other line of the file stays the same, and moving the row back writes the original file again.
- **The three editors that move rows all go through the one shared splice (`spliceYaml` in `src/concepts/world-building/yamlSplice.ts`):**
  - the Bundles page's rows (`BundlesPanel.tsx`);
  - the machine editor's List pop-up (`MachineStateEdit.tsx`);
  - Endings (`StudioEndings.tsx`).
- **How it works.**
  - `alignItems` treats a row that is out of the common order but equal to a row on the other side as moved, not as removed and added. Two identical rows ("twins") are paired in order.
  - `walkSeq` puts a moved row back as its own span of source text (`itemSpan`).
  - A row that moved and also changed has the change spliced into its own text (`movedItemEdited`). This can only happen when the rows are aligned by id.
- **Remove, add and edit.** Removing a row removes its span. Adding a row writes a fresh row next to its neighbour's span. Editing a row in place rewrites only the scalar that changed, and the row's comment stays.

## Decided

- **The attachment rule.** A row owns:
  - the comment lines directly above its dash, at the dash's column; a blank line, or any other line, ends the run;
  - its own lines, with any comment on its last line;
  - the comment lines directly below it that are indented deeper than the dash.

  Why: this is how the castle writes its comments. All 61 comment blocks above a row sit at the dash column, and the first `time` row's hand edit sits directly under its key. A comment above the list's key, or one set off from the first row by a blank line, is the list's and stays where it is.

- **Leftover rows are not paired in order across the whole list.** If they were, deleting one row and adding another would hand the deleted row's comment to the new row, which is worse than dropping it. So a row with no id that is moved and edited in the same write counts as one row removed and one added. No editor does both in a single commit.
- **Twins pair in order.** Among identical rows, the k-th old row is paired with the k-th new row. Their values are equal, so nothing written changes, and moving one twin past another row carries the twin's own comment. Swapping the two twins with each other changes no value, so that write leaves the file as it was.

## Found

- **There is a third caller.** `StudioEndings.tsx` moves endings through the same splice. In the castle, the "Hand edit (rpg-project#716 …)" block above `king-deposed` (`the-mad-king.yaml` ~:387–391) reads as a note on the whole list, but by the rule it belongs to `king-deposed`, so it moves with that row. On `dev` it was dropped.
- **List-level notes written directly under a key go to the first row.** Examples are the `options` notes (~:1568, ~:1744), ~:1909, and `dispositions` (~:307). No editor moves those lists today. To keep such a note with the list, put it above the key or leave a blank line after it.
- **Compact nested rows (`- - 3`) corrupt on some writes, and this is pre-existing on `dev`.** The castle writes its ground-paint cells this way (~:1117–1165). Rows whose dash does not start the line still take the old path, which can write the wrong value or unparseable output. Nothing re-parses the output before it is written. This is tracked separately, outside this PR.
- **Two moves plus an edit in one write (`[a,b,c,d]` → `[d,bb,c,a]`) can lose `b`'s comment.** The common subsequence anchors differently in that case. `dev` does the same, and no editor makes that write.

## Mistaken

- **My first fix only changed re-insertion.** I assumed alignment already paired a swapped row as a move. It did not: a swap keeps only one row in the common order. Seeing the castle test still fail showed it.
- **The first in-order fallback ran before move pairing.** In `[D,B,C,A]` that paired A with D as an edit. Move pairing now runs first.
- **The first move-and-edit test never reached `movedItemEdited`.** The edited row was the one that stayed, not the one that moved. The review caught it with a mutant. The test now moves the edited row, and replacing the call with `null` makes it fail.
- **The PR named two callers.** Endings is a third, and the review found it.
